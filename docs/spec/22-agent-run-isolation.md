# 22 — Autonomous Run Isolation and Capability Boundaries

Decision: **ADR-0018**, with ADR-0012 for the GitHub identity. This spec is the authoritative source for how an autonomous **worker run** is isolated and what it may reach. Spec 19 §5 owns the issue-claim protocol (including AGENT-03 and AGENT-09), and spec 21 owns GitHub App identity and tokens (AGENT-01, AGENT-04). Other documents refer here instead of repeating these rules.

These requirements bind the bubbles-agent implementation (X-000, X-001). They incorporate the isolation and crash-consistency findings of the reviewed implementation design. Where an implementation design disagrees with this spec, this spec wins.

## 1. Trust model

A worker run executes text that outsiders can influence: issue, PR and review comments reach its prompts, and repository dependencies, install scripts and tests run inside it. So **a run is untrusted**, and runs are untrusted **towards each other**. Everything a run needs from the outside world is provided by trusted components that check each request.

| Component | Identity | Trusted | Holds | Reachable by runs through |
|---|---|---|---|---|
| Token helper (`agent-token`, 21 §5) | `agents` | Yes | The App key | Nothing. Only the supervisor service connects (AGENT-15) |
| Supervisor and **publication broker**: one process, `bubbles-agent-supervisor.service` | `agent-worker` | Yes | The run registry, issue-claim state, per-operation installation tokens | The broker socket |
| **Model proxy** | `agent-llm` | Yes | The model-provider key | The model socket |
| **Package proxy** | its own dynamic uid | Yes | No credential | The package socket |
| **Worker run**: launcher, Claude Code and everything they start | one dynamic uid per run, class `agent-run` | **No** | Its worktree and its own model capability only | — |

`agent-run` names the class of run identities and a static supplementary group whose only use is permission to connect to the three run-facing sockets. It is never a shared uid. systemd, the kernel and root are trusted. Root, which includes `charles` through `sudo` and `docker`, can read every identity (21 §5 residual risk).

### 1.1 Identity chain per boundary

No trusted component accepts a run-id, `claim_id`, repository, branch, PR, model or budget identity because a run wrote it in a request. Each identity comes from the kernel or from the supervisor's registry:

| Boundary | Chain |
|---|---|
| GitHub | run, authenticated by `SO_PEERCRED` uid and pidfd cgroup on the broker socket (AGENT-02) → registry row and author-filtered GitHub re-read under the issue lock (AGENT-03) → token helper, which accepts only the supervisor service (AGENT-15) → GitHub, one token per operation (AGENT-04) |
| Model | run → its loopback forwarder → the model socket, where the proxy matches the caller's uid and cgroup to the binding the supervisor registered and to the run's capability (AGENT-12) → the fixed provider upstream (AGENT-05) |
| Packages | run → its loopback forwarder → the package socket, where the proxy matches the caller's uid and cgroup to the supervisor's binding (AGENT-11, AGENT-12) → the fixed registry upstream |
| Administration | supervisor service only, authenticated by uid and cgroup (AGENT-15). Worker runs can't see these sockets (AGENT-17) |

## 2. Requirements

| ID | Requirement |
|---|---|
| AGENT-02 | **Publication broker.** The broker is the only component that writes to GitHub on a run's behalf (AGENT-01). It identifies a caller only from the kernel: the `SO_PEERCRED` uid must be the dynamic uid systemd assigned to a live run unit, a pidfd on the peer must show that unit's cgroup and still refer to a live process, and the run registry row for that unit must record the same uid. Requests follow a closed schema with size limits and never carry a repository, issue, branch, PR or run-id; those come from the registry row. Before every mutation the broker applies, in order: schema, caller, fixed repository, the registry branch under `refs/heads/agent/<worker-id>/` (never `main`, tags or deletions), authorization (AGENT-03), content checks (fast-forward only, unless Charles requested a rebase; no `.github/workflows/` changes or gate suppressions; no credential patterns in outgoing text), a per-operation token (AGENT-04), and a credential-free audit event. It never executes run input: commits arrive as a git bundle passed as a file descriptor and are fetched into the broker's own bare repository with hooks disabled. It also offers a run whose claim is the active winner a parameterless read-only **`fetch`**, which returns a bundle of `main` and the run's own registry branch, fetched anonymously into the broker's bare repository |
| AGENT-05 | **Model-access boundary.** A run MUST NOT contain a reusable model-provider credential: no provider API key, OAuth or session token, login file or keychain entry, in its environment, files or memory. Model access goes only through the model proxy, the only identity that can read the provider key (through systemd credentials, never an environment variable or a file a run can reach). The proxy uses a fixed upstream with TLS verified for its name, ignores client-supplied host, URL and credential headers, has no proxy settings of its own, and never falls back to another destination: if the upstream can't be resolved or reached, the request fails and the key goes nowhere. It enforces allowlists for paths, models and beta features, caps on tokens and body size, and per-run rate and spend budgets. It refuses requests that ask the provider to make network connections on the run's behalf (MCP servers, server-side web fetch or search, code execution, or any tool type not allowlisted). Its upstream egress is limited by `IPAddressAllow=` to the provider's published API ranges plus the local resolver stub. If no published range covers the API, the allowlist is never widened to `any`. If the coding agent can't run against this boundary, implementation stops: a raw key in the run is never the fallback |
| AGENT-06 | **Per-run execution identity.** Each run executes in its own systemd service unit, `bubbles-run-<run-id>.service`, started by the supervisor (a transient unit, or an instance of a static template if the polkit rule can't match transient names). The unit sets `DynamicUser=yes`, which gives the run its own uid and implies `NoNewPrivileges`, `RestrictSUIDSGID`, `ProtectSystem=strict`, a private `/tmp` and `RemoveIPC`. It also sets `SupplementaryGroups=agent-run`, `PrivatePIDs=yes`, `ProtectProc=invisible`, `PrivateIPC=yes`, `PrivateNetwork=yes` (AGENT-10), `ProtectHome=yes`, `UMask=0077`, per-run CPU, memory and task quotas, and the default-deny filesystem and socket view of AGENT-17. The startup barrier of 19 §5 is preserved: the barrier pipe is the unit's stdin, and end-of-file means exit without acting. The supervisor signals a run only through its unit or through a pidfd whose start time matches the registry. A polkit rule lets `agent-worker` start, stop and kill only units named `bubbles-run-*` |
| AGENT-07 | **Private state and worktree ownership.** A run's worktree, `HOME`, Claude configuration directory and git objects live in its own `StateDirectory=`, and its package caches in its own `CacheDirectory=`, both under systemd's root-only private parent and owned by the run's dynamic uid. The environment points every cache and XDG directory there: `XDG_CACHE_HOME`, the npm cache and the pnpm store under the cache directory; `XDG_CONFIG_HOME`, `XDG_DATA_HOME` and `XDG_STATE_HOME` under the run's `HOME`; `XDG_RUNTIME_DIR` unset. Nothing falls back to a shared path. The worktree is built only from broker `fetch` bundles, is never shared between runs, and is never read or executed by the supervisor or broker. A handoff successor rebuilds its worktree from the remote branch, never from its predecessor's directory. The coding agent, skills and browsers are pinned, root-owned, read-only installs. Writable directory binds are never used; the only writable binds are the three endpoint sockets of AGENT-17 |
| AGENT-08 | **Sibling-run isolation.** A run MUST NOT read, modify, signal, trace, inject into, impersonate or reuse anything that belongs only to another run: its processes and `/proc` entries; its worktree, git objects and local commits; its `HOME`, XDG, cache and Claude state; its temporary files and IPC objects; its path or abstract Unix sockets and its TCP or UDP listeners; its model capability; its broker identity and requests. This holds while both runs live, after the other run is killed, parked or handed off, and when a uid, PID or unit name is reused. Kernel uid checks, `PrivatePIDs=`, `ProtectProc=invisible`, private state (AGENT-07) and private network namespaces (AGENT-10) enforce it. The launcher adds Landlock scoping of signals and abstract sockets as defence in depth |
| AGENT-10 | **Network isolation.** A run has no ambient network authority. `PrivateNetwork=yes` leaves it a loopback interface only, so it has no route to the Internet, to the host's loopback services or to another run, on IPv4 or IPv6, by name or address, on any port. It gets no DNS: every name it uses resolves locally, and recursive DNS from a run is refused because it would be an exfiltration channel. `SocketBindDeny=` refuses every explicit UDP bind on IPv4 and IPv6. Its only external paths are the three endpoint sockets of AGENT-17. Before any repository code runs, the trusted launcher starts loopback forwarders inside the namespace for the model and package sockets; the broker client connects to the broker socket directly. A forwarder runs as the run's own uid, so bypassing it gains nothing: the proxies identify the run from the kernel credentials of the socket connection. No tunnel or general-purpose proxy exists: a host allowlist on a tunnel is not acceptable, because untrusted code can bring its own GitHub or npm token and write through an allowed host |
| AGENT-11 | **Package proxy.** The package proxy is a run's only path to packages. It accepts only `GET` and `HEAD` on package-registry metadata and tarball paths, and refuses other methods (so no publication), request bodies, credential and cookie headers, and every other path. Its upstream is fixed to `https://registry.npmjs.org`, port 443, TLS verified. It follows redirects only to the same host, rewrites tarball URLs to point back at itself, resolves the fixed name itself, and refuses loopback, private, link-local, carrier-grade NAT and unique-local addresses on IPv4 and IPv6 (with the same ranges in its unit's `IPAddressDeny=` as a backstop). It identifies the calling run only from the kernel: the `SO_PEERCRED` uid and pidfd cgroup of the connection must match a live binding the supervisor registered (AGENT-12). A run-id or any other identity in the request is ignored, and client headers outside its allowlist are dropped. Per-run request limits, budgets and the audit record (run-id, path, status, bytes) use that binding. It may cache responses, because runs can only read. Accepted residual risk: §4 |
| AGENT-12 | **Run-endpoint binding and revocation.** For each run, the supervisor registers a binding with the model proxy and with the package proxy over their admin sockets (AGENT-15): run-id, unit name, unit cgroup id, dynamic uid, expiry, run state and limits, plus, for the model proxy, the run's random capability. It registers them only after the run's registry state is `winner` (19 §5, AGENT-09). A proxy serves a connection only if the caller's `SO_PEERCRED` uid and pidfd cgroup match a live binding (for the model proxy, also the binding the presented capability names) and the run is still `winner` and unexpired. The supervisor revokes both bindings before or with every authority-reducing transition: loss, release, abandon, parking intent, `request_info` intent, handoff (old run), stale or orphaned recovery, unit exit and runtime expiry. Bindings and capabilities live only in the proxies' memory, so a proxy or host restart revokes all of them. A binding, capability or run-id known to another run, or presented after reuse of a uid, PID or unit name, grants nothing |
| AGENT-13 | **Cleanup and restart.** Runs are never resumed. A new run in the same slot continues only through a fresh claim or a supervisor handoff (19 §5) and rebuilds its state (AGENT-07). On unit stop, the supervisor revokes the run's capability and closes its registry row before systemd releases the uid. Trusted cleanup removes the run's state and cache directories (`ExecStopPost=`, then the supervisor's unit cleanup, then a `systemd-tmpfiles` age rule as backstop); leftovers stay root-only until removed. A parked run's unit is stopped. Restart reconciliation (19 §5) treats each run unit as the run's cgroup, re-reads GitHub first, and follows AGENT-09 |
| AGENT-14 | **Adversarial test suite.** Each boundary in this spec, in 19 §5.1 and in 21 §5 has an experiment that must fail for the attacker and succeed for the legitimate path, with a mock GitHub API unless Charles approves a live check. At minimum:<br>**Credentials:** a run can't read or use a GitHub token, the provider key or another run's capability.<br>**Siblings:** two concurrent runs can't reach each other's processes, `/proc`, state, caches, sockets (TCP and UDP, IPv4 and IPv6) or broker identity; reuse of a uid, PID or unit name resurrects nothing.<br>**Network:** a run has no route out and no DNS, and its UDP binds fail; git works only through broker bundles, even with a token planted in the run.<br>**Socket view (AGENT-17):** each of the three endpoints works; a known host socket (D-Bus, journal, systemd, token helper, an admin socket) and a socket created on the host after the unit started are absent and can't be connected; a sibling's sockets are unreachable; the run's root shows only the skeleton and its explicit binds.<br>**Model and packages:** the model proxy refuses server-side network tools and exposes nothing when its upstream fails; the package proxy refuses publication, credentials, foreign paths, cross-host redirects and rebinding to private addresses; audit records name the right run; a forged run-id in a header or query changes nothing; run B can't spend A's budget or appear as A; after A's release or unit stop, and after uid or unit-name reuse, A's bindings refuse.<br>**Token helper (AGENT-15):** the supervisor mints a token whose permissions equal the requested operation class; a run can't connect; another process running as `agent-worker` outside the supervisor unit is refused; a request naming another repository or a permission outside the class is refused.<br>**Host preflight (AGENT-16):** with systemd older than 257, without PID namespaces, or with a run unit whose PID namespace isn't private, the supervisor refuses to run and records why; no run starts on weaker settings.<br>**Initial claim (AGENT-03 A1):** a fresh run in `released` state gets exactly one marker, whose comment ID is bound as its `claim_id` before any other request is accepted. The crash and retry cases:<br>• crash before the post: nothing is bound, and a retry claims once;<br>• post succeeded but the response was lost, or a crash came before binding: a retry or restart adopts the existing marker and posts nothing;<br>• `begin` repeated after binding: returns the recorded state, with no second marker;<br>• a forged, non-App or edited comment that looks like the run's marker is ignored;<br>• another run's `begin` can't bind that marker, and a request that supplies a `claim_id` is rejected;<br>• two App-authored markers for one run: nothing is bound, the run is stopped and the claim goes to supervisor recovery;<br>• a run whose row isn't `released`, or already has a `claim_id`, is refused;<br>• later requests and broker steps with a missing or different `claim_id` are refused.<br>**Recovery (AGENT-03, AGENT-09):** with a lost registry and unambiguous App-authored history, the supervisor records a recovery intent and then posts only the allowed recovery release; with ambiguous history it posts nothing and lists the issue for manual recovery; forged, non-App or edited markers are ignored; a run can't invoke recovery, handoff or reconciliation; recovery never creates a second winner; and each crash point of AGENT-09 recovers with no permission gained.<br>The suite is re-run after any change to users, units or these components, and extends the negative isolation test of 21 §7 |
| AGENT-16 | **Host prerequisites and preflight.** Autonomous execution requires systemd 257 or later (`PrivatePIDs=` was added in 257), cgroup v2, and a kernel with PID, network and mount namespaces, `SO_PEERPIDFD` (Linux 6.5 or later) and Landlock ABI 6 or later. At startup the supervisor checks each one and refuses to start any run if one is missing. It never falls back to a shared PID namespace or any weaker setting. systemd ignores `PrivatePIDs=` on a kernel without PID namespaces, so each run is also checked before its barrier is released. The trusted launcher, which must be PID 1 in its own namespace, confirms that before reading the barrier: PID 1, only a loopback interface, and the root of AGENT-17. If any check fails, it exits without acting. The supervisor reads the run's `NSpid:` line in `/proc/<pid>/status`, which must show a nested PID namespace, and confirms the unit's private settings through systemd. If any check fails, the supervisor kills the unit, records the refusal and starts no further runs until the host is fixed. Deployment evidence: on 2026-10-06 the deployment host ran systemd 257 and Linux 6.12 |
| AGENT-17 | **Default-deny filesystem and socket view.** A run unit starts from an empty root. `RootDirectory=` points at a root-owned, read-only skeleton that holds only mount points and the merged-`/usr` symlinks. Nothing from the host appears unless the unit binds it explicitly:<br>• `BindReadOnlyPaths=` for `/usr`, the pinned coding agent, the skills and the browsers, plus single files under `/etc` that X-000 shows are needed;<br>• the API filesystems: `/proc` for the run's own PID namespace, `/sys`, and a minimal `/dev` with `PrivateDevices=yes`;<br>• a private `/tmp`;<br>• the run's `StateDirectory=` and `CacheDirectory=`.<br>Exactly three pathname sockets are bound in, writable so the run can connect, at fixed paths under `/run/bubbles/`: the broker socket, the model socket and the package socket. They are the host's socket inodes, bind-mounted. The forwarders of AGENT-10 bridge loopback TCP to the model and package sockets. No other host pathname socket is present in the run's view: no D-Bus, systemd or journal socket, no token helper or admin socket, no container or VPN daemon socket, and nothing from another run. A socket created on the host later doesn't appear either. Exposing a host directory and hiding selected paths is not acceptable. A file found missing at X-000 is added by an explicit read-only bind of that single file. X-000 also confirms that `StateDirectory=`, `CacheDirectory=` and the socket binds work together with `RootDirectory=` and `DynamicUser=`. If they don't, the design is revisited, never widened to the host root |

## 3. What a compromised run can still do

Within its own claim, a run can publish to its own branch and PR, comment on its own issue or PR, spend its own model budget until revocation, and fetch public packages. That is bounded by the branch namespace, the gates, `gate-integrity` and Charles's review of every merge (ADR-0011). It cannot publish after losing, releasing or parking its claim; write to another branch, issue, PR or repository; obtain a token, the App key or the provider key; act as another run; or reach any destination this spec doesn't list.

## 4. Accepted residual risks

The architecture doesn't eliminate every possible exfiltration channel. Charles accepted these explicitly when approving this amendment (2026-10-06):

- **Package-retrieval covert channel.** An untrusted run may encode a limited amount of information through the choice and timing of legitimate public package requests made through the package proxy (for example, download counts of a package someone controls). The acceptance is **conditional** on these mitigations staying in force: no ambient direct Internet access from a run (AGENT-10); package traffic only through the package proxy; fixed, approved upstreams; read-only retrieval; no package publication; no credential forwarding; redirect and destination controls; per-run request limits and audit metadata (AGENT-11). If any of them is removed, the acceptance lapses and the risk needs a new decision.
- **Model prompts.** Run data reaches the model provider under this deployment's account, as prompt content. An outsider can't read it there.
- **Kernel exploits, timing side channels and resource contention** (bounded by unit quotas).
- **Root on the host**, including `charles` (21 §5).
